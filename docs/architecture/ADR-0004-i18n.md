# ADR-0004: i18n with next-intl, en + pl

Status: accepted · 2026-09-12
Part of: SPEC-0001

## Context
First users are Polish agencies; the product targets EMEA, so English is the default. MVP needs two locales without hard-coded strings creeping in.

## Options
1. **next-intl** — ICU messages, RSC-friendly, per-locale JSON files, works with Next 16 app router.
2. **react-i18next** — mature but client-centric; worse RSC story in app router.
3. **Ad-hoc dictionary module** — zero dependency, but loses plurals/ICU and linting; drifts fast.

## Decision
Option 1. Rules:
- All product strings in `messages/{en,pl}.json`; Polish is complete alongside English (no partial-locale runtime fallback to keys — fallback locale is `en`).
- User locale = user profile field; tenant has a default locale. URL carries no locale segment in MVP (locale from session), avoiding route duplication.
- Server components format via `next-intl` server API; dates/numbers use the user locale.
- Tenant *content* (customer messages, KB articles) is never machine-translated in MVP.

## Consequences
- Every UI string goes through the message catalog — enforced in review.
- Adding a locale = one JSON file + locale code in the enum; no route changes.

## Reversal trigger
SEO-driven public marketing pages needing localized URLs → add `[locale]` routing then, app UI unchanged.
