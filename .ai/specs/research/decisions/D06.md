# D06 — Coordination through PostgreSQL; no Redis, no Kubernetes primitives
- Date, owner: 2026-09-21 (decision recorded in docs/production-readiness-plan.md §3, written 2026-09-04); ownership confirmed by Kamil Mastalerz in the discovery session
- Context and the options weighed: Redis/BullMQ queues + K8s leases (what the api's worker uses today) vs. Postgres-only coordination.
- Decision and why: job claiming via `FOR UPDATE SKIP LOCKED` with claim tokens and expiring leases; uniqueness constraints protect operation ids, IMAP message ids, and the active send; presence as a Postgres heartbeat with the current 45-second expiry. Web and worker are two run modes of one image, both stateless.
- Consequences, and what would make us revisit it: the api's current BullMQ/Redis dependency is scheduled for replacement in the migration; uncertain SMTP/AI outcomes are still never auto-retried. Revisit only if Postgres-based queueing fails the plan's acceptance tests.
- Status: active
